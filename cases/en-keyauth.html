C# / ASP.NET Core · licensing · Unity client

KeyAuth

Client Unity applications shipped without control: no server-side key issuance or accounting, and already distributed builds could not be broken by a change in the verification scheme.

GitHub
01

Problem

Client Unity applications shipped without control: no server-side key issuance or accounting, and already distributed builds could not be broken by a change in the verification scheme.

02

Constraints

Already distributed Unity builds must not break when the scheme changes; the server must enforce activation limits and identify the application, and network failures must not grant access.

03

Solution

A standalone ASP.NET Core API: key registration and activation with activation counting, server-side application-name verification and compatibility with previously shipped clients; the Unity client reads the key and receives the server decision.

04

Outcome

A working client-to-server activation path with activation accounting and support for shipped builds; per the client, unlicensed copies stopped running without a valid key (author attestation, not an independent measurement).

05

Verification

Public ASP.NET Core backend and Unity client on GitHub, activation-accounting and application-name checks, plus 2024 client correspondence confirming delivery and post-delivery fixes (private, quoted without content).

06

My ownership

Server-side key and activation model, the API, the Unity client, backward compatibility with older builds, and integration support.
